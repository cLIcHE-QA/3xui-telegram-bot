# Внешние платёжные ссылки: проектный контракт Platega и будущих PSP

> **Статус на 2026-10-11, Europe/Helsinki: PLANNED / NOT IMPLEMENTED.** Это инженерная спецификация для [Issue #336](https://github.com/cLIcHE-QA/3xui-telegram-bot/issues/336), **не инструкция по включению реальной оплаты**. Последний опубликованный GitHub prerelease — `v5.0.0-rc.9` (tag SHA `13fdbe8bccfbe92cffc4117b79083bbdcad5a8db`); последнее operator-reported production deployment — `v5.0.0-rc.9` (tag SHA `13fdbe8bccfbe92cffc4117b79083bbdcad5a8db`, independent VPS/build attestation PENDING). Новый PSP ещё не подключён, merchant approval и production acceptance отсутствуют.

## 1. Принятое продуктовое решение

- Предусмотреть **два независимых способа оплаты**: существующий Telegram Stars (`XTR`) и будущую альтернативу в `RUB`, сначала через [Platega](https://platega.io/ru), затем при необходимости через другие PSP.
- Целевой UX для RUB: **клиент выбирает тариф в Telegram-боте → бот создаёт индивидуальный заказ и выдаёт URL платёжной страницы Platega → клиент платит на сайте провайдера → сервер самостоятельно подтверждает транзакцию → тот же `Order → Payment → Entitlement → ProvisioningEngine` обновляет VPN → бот уведомляет пользователя**. Это не ручная выдача и не перевод денег напрямую боту.
- Услуга — **собственный VPN на арендованных VPS**, не перепродажа подписки третьего лица. Ожидаемый статус исполнителя по договору — **физлицо на НПД (самозанятый)**. Merchant acceptance, налоговая и правовая оценка не подтверждены одним этим решением.
- **Решение оператора от 2026-10-11:** оператор уведомлён о риске альтернативной оплаты цифровой услуги из Telegram-бота и намерен проектировать/интегрировать выбранный вариант. Это позволяет **планировать и разрабатывать offline adapter**, но **не означает, что Telegram разрешил его использование**, и само по себе не разрешает publication, production deployment, реальные платежи или расширение пилота. Отдельный explicit rollout approval обязателен.
- Источники требования платформы: [Telegram Stars for digital goods](https://core.telegram.org/bots/payments-stars), [Bot Developer Terms](https://telegram.org/tos/bot-developers). По действующим публичным правилам Telegram цифровые услуги внутри ботов/Mini Apps должны оплачиваться Stars даже при наличии стороннего сайта. Практика других ботов не является platform approval. Residual **Telegram platform risk: ACCEPTED FOR DESIGN BY OPERATOR; COMPLIANCE NOT VERIFIED**. Никаких методов сокрытия платежа или обхода платформенных проверок не проектировать.

## 2. Trust boundaries и данные

1. **Приватная owner-связь:** бот аутентифицирует Telegram identity и создаёт серверный `commerce_orders` с `telegram_id`, `plan_id`, зафиксированными `amount_minor`, `currency=RUB`, сроком, версией условий и opaque `order_reference`. **Публичная платёжная ссылка не содержит Telegram ID, subscription URL, username, секреты, внутренний ID заказа или права доступа**.
2. **Создание платежа:** из серверного заказа `CheckoutService` обращается к отдельному `PlategaCheckoutProvider` (не к Stars flow) с внутренним idempotency key, нормализованными суммой, валютой и непрозрачным `payload`/order reference. Ссылка должна быть **уникальна для заказа**; дублированный пользовательский callback/нажатие возвращает существующий действующий checkout, а не плодит платёжные сессии.
3. **Приватные PSP metadata:** в документированном API Platega для отдельных merchant categories требуется `metadata.userId`; заранее согласовать у менеджера, можно ли использовать стабильный псевдоним вместо Telegram ID. Если PSP требует настоящую идентификацию — передавать только минимально требуемую информацию **на серверной стороне API**, не в публичном URL, после legal/privacy review. Никаких незадокументированных запросов данных.
4. **Контракт URL:** использовать только полученный от подтверждённого provider adapter `https://` checkout URL с allowlist разрешённых провайдером hosts; отключить любые произвольные/redirect URL из query или webhook. Не класть полный checkout URL и платежные токены в audit/CI/logs; URL может быть временным credential.
5. **Изоляция:** отдельные PSP credentials per merchant/provider, в private `.env` или secret storage. Никогда не переиспользовать Telegram bot token, Direct Admin, Master 3x-ui, Deploy Agent и PSP секреты. Provider adapter не имеет доступа к host shell/Docker socket.
6. **Срок ссылки:** явный TTL из PSP, revocation/expiry состояния в SQLite. Не считать `PENDING`/redirect/proof screenshot оплатой; late confirmation/expired order трактовать по documented reconciliation, не допуская повторного начисления.

## 3. Platega adapter, не предполагать generic HMAC

Первичная версия контрактов провайдера: [API overview](https://docs.platega.io/), [создание ссылки без метода — `POST /v2/transaction/process`](https://docs.platega.io/создание-платежной-ссылки-без-заданного-метода-33845703e0), [создание с методом — `POST /transaction/process`](https://docs.platega.io/создание-ссылки-на-оплату-29203843e0), [проверка статуса — `GET /transaction/{id}`](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0), [callback](https://docs.platega.io/callback-об-изменении-статуса-транзакции-29209725e0). Перед кодовым PR проверить точный актуальный контракт и разрешённые методы у merchant manager.

- **Create:** ответ PSP содержит собственный `transactionId`, `url` или `redirect`, `status=PENDING`, `expiresIn`. Идентификатор PSP генерируется самим провайдером. `order_id`/idempotency — **внутренняя** гарантия; наличие provider-side dedup не предполагать. При timeout создания помечать исход `unknown` и сверять с PSP, не отправлять blindly новый create.
- **Callback:** по опубликованному контракту Platega отправляет `X-MerchantId`, `X-Secret` и status `CONFIRMED`, `CANCELED`, `CHARGEBACKED` на HTTPS endpoint. **Это не универсальная `X-Payment-Signature` HMAC-схема** из `payment_webhook.py`. Реализовать отдельную проверку merchant ID и secret constant-time compare, TLS, ограничение payload/rate, отсутствие логирования credentials, и **обязательный authenticated `GET /transaction/{id}` read-back** перед financial confirmation. Не заявлять, что Platega подписывает тело HMAC, если такой контракт не согласован.
- **Binding:** доверять только заранее сохранённой паре `(merchant/provider, provider_transaction_id)` → `payment/order` с проверкой внутреннего owner, суммы (в корректных единицах), валюты, состояния заказа и уникального provider reference. `payload`, `metadata`, `return`/redirect, query `telegram_id`, переданный callback user ID **не авторизуют** provisioning или перепривязку owner. Несовпадение → fail closed + журнал расследования.
- **State machine:** `PENDING/UNKNOWN` не начисляют entitlement; `CONFIRMED` от API read-back → ровно одно атомарное применение payment → order → entitlement; `CANCELED` → без выдачи; `CHARGEBACKED`/refund → отдельное финансовое событие и согласование с политикой отзыва оплаченного периода, не молчаливое удаление аккаунта. Сохранять raw provider status и normalized status отдельно.
- **Delivery:** webhook можно получить несколько раз, раньше/позже browser redirect, либо после рестарта. Persisted event journal + unique constraints/reconciliation блокируют duplicate renewal, duplicate quota reset и повторную нотификацию. Не подтверждать delivery без verified 3x-ui postcondition; при unknown provider или provisioning — `PENDING reconciliation`, без blind mutation retry.
- **Read-back:** проверять exact PSP transaction, amount, currency, merchant, paid state. Для неопределённых статусов запрашивать provider status в bounded retries с backoff; технические статусы и финальная выдача должны быть независимо аудируемы.

## 4. Возвраты, юридический текст, чеки и UI

- **Stars (ближайший `rc.10`):** [#433](https://github.com/cLIcHE-QA/3xui-telegram-bot/issues/433) — добровольное окно 14×24 часа от подтверждения **каждой** покупки и вычитание полной приобретённой длительности после подтверждённого полного возврата. Примеры: 30d→0 (доступ выключен), 30+30→30 (доступ остаётся), 15 дней использовано и 45 осталось → минус 30 = 15. При нехватке дней clamp до 0, без долга будущим покупкам. Повтор refund не списывает срок повторно. Законные требования, partial refunds и forced chargebacks — отдельно, не сводить всё к простой формуле дней.
- **RUB/Platega (последующий milestone):** связать PSP refund/chargeback с тем же provider-neutral journal `payment_id → entitlement adjustment`; PSP-confirmed refund и provider `CHARGEBACKED` — разные бизнес-события, требующие документированного решения и postcondition проверки. Окно и порядок добровольных возвратов должны совпадать с утверждённой [#436](https://github.com/cLIcHE-QA/3xui-telegram-bot/issues/436) политикой для соответствующего метода; дату/версию действовавшей policy записать на заказ.
- **Client Portal:** [#434](https://github.com/cLIcHE-QA/3xui-telegram-bot/issues/434) — ненавязчивое объяснение добровольного срока и кнопка «Условия возврата» **перед** отправкой Stars invoice; при появлении RUB checkout — та же ссылка на версионируемую политику без утверждения, что PSP уже активен.
- **Support:** [#437](https://github.com/cLIcHE-QA/3xui-telegram-bot/issues/437) — read-only памятка `/admin → Платежи → Политика возвратов`, отдельные провайдеры, записи, эскалация Owner; доступ к памятке не даёт полномочий на real refund. Расходы/сроки/возможность отказа от услуг должны быть юридически проверены, 14 дней — не запрет обязательных прав.
- **Исполнитель на НПД:** договор/merchant onboarding должен подтверждать допустимость собственного VPN-сервиса и доходов НПД; порядок выдачи/аннулирования чека («Мой налог»/интеграция), merchant statement reconciliation, комиссию и chargeback expenses. Отдельный legal/privacy review РФ до публичной активации; ничего не записывать в публичные GitHub artifacts о реальных клиентах, реквизитах или токенах.

## 5. Реализация по отдельным PR и регрессии

1. PSP contract/client adapter: точные API модели, provider-specific auth, create/status, TTL, response validation, 3x-ui privilege isolation, timeout/unknown, sandbox fixtures.
2. SQLite migration и integration: уникальные `provider_transaction_id`, `order_id`-привязка, persisted attempt/checkout URL TTL, idempotent journal/event + policy version, CAS on order state. Старые Stars orders и schema v13 сохраняются без повреждения.
3. Webhook ingress: provider secret + read-back, body bounds, TLS, RBAC/owner isolation, duplicate/delayed/out-of-order, mismatch/refund/chargeback, signed return state only for UI, no implicit payment success.
4. Client UX/owner controls: разные методы Stars/XTR и PSP/RUB не смешиваются, доступны только на разрешённом этапе rollout, per-provider kill switch независимо от existing Client Portal and Stars flags. Секреты не выводятся через admin UI. `/paysupport` и legal Terms не теряются.
5. Targeted CI: exactly-once fulfilment при duplicate webhook; unknown checkout response; callback spoof; wrong merchant/amount/currency/order; IDOR/forged checkout owner; expired URL; provider downtime; restart; reconciliation; refund/chargeback; 0-day clamp; redacted logs; RBAC and feature-flag fail-closed. В каждой реализации обновить `docs/CLIENT_SETUP.md`, `docs/ADMIN_SETUP.md`, `docs/V5_PRODUCTION_ACCEPTANCE.md`, `CHANGELOG.md` и `docs/ROADMAP.md` согласно actual diff и Living Docs.
6. Release/deploy: только отдельные approved PR, required `test`/`title`, immutable RC tag, явное operator-approved deployment и затем **3–4 новых узких** scoped smoke с Roadmap/Issues checkpoint. Не повторять waived/пройденные сценарии и не выполнять реальные покупки/возвраты для «проверки документа».

## 6. Известные нерешённые вопросы

- Platega merchant/KYC approval для собственного VPN и статуса НПД; способы оплаты, тарифные limits, статус merchant environment, sandbox и webhook credential rotation.
- Требуется ли provider `metadata.userId` (и допускается ли pseudonymous ID), какой именно contract/API version и есть ли dedup creation на стороне PSP.
- Финансовая policy RUB: сроки/частичные/forced chargebacks, способ расчёта законных требований, обязательная фискализация и возврат чека.
- Telegram-platform compliance: риск признан оператором, но внешние ссылки для цифровых услуг внутри бота противоречат публичному Stars-only правилу; ни разрешение, ни положительное юридическое заключение не получены. Это residual risk, а не evidence PASS.
- Отдельный выбор момента запуска PSP относительно `rc.10`: **этот документ не расширяет scope `rc.10` автоматически**; выпуску PSP требуется собственный scope, CI, release-prep, approval и production acceptance.
