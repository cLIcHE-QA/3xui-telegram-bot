## Дополнительная статическая проверка рисков для будущего rc.18.4

Основание: read-only сверка неизменяемого исходного кода `v5.0.0-rc.18.3` (`device_presentation.py`, `device_model_resolver.py`, `customer_provider_xui.py`), действующих тестов #827/#830 и изолированное воспроизведение логики regexp в Python. **Это не CI, не VPS/Telegram smoke и не подтверждение, что каждый риск встречался в production.** Пять исходных наблюдений — operator-reported, остальные пункты ниже — аналитические edge cases.

1. **Пропущенные приложения / расширенные UA (воспроизводимый parser fallback):** `Happ/v1.2.0`, `Happ/1.2.3-beta`, `NekoBox/Android/1.4.1`, `INCY/…/android Dalvik/…`, `Karing/… platform/ios;…` отклоняются действующим `fullmatch`. Лишний конечный пробел тоже отклоняется. Длинный UA (свыше 256 ASCII-символов) отбрасывается до разбора имени. Для Karing в предоставленной admin-карточке есть только первые 160 символов — действительная длина upstream UA не доказана.
2. **Ложная подпись VPN-клиента (воспроизводимый false positive):** самостоятельно взятые `Dalvik/2.1.0`, `okhttp/4.12.0`, `Mozilla/5.0` и `curl/8.0.1` проходят `recognized_vpn_app` и выводятся как заявленное имя приложения, хотя это технические HTTP/runtime идентификаторы. Нельзя считать синтаксически безопасный префикс доказательством VPN-приложения. Полные обычные browser-UA часто отбрасываются, речь только о конкретных коротких форматах.
3. **Android emulator / технические модели:** `Google sdk_gphone16k_arm64` и другие имена с `sdk_gphone`, `emulator`, `generic_x86_64` при подтверждённом Android могут остаться исходными кодами: нет bounded emulator fallback, а составные модели с пробелами минуют Android Device index. Проверять строго заданные эмуляторные формы и сохранять настоящие `Pixel`/`Galaxy`.
4. **Невалидный OS-префикс распознаётся платформой (воспроизводимо по `startswith`):** `Androidish` классифицируется как Android, `iOSFake` как iPhone, `macOSfake` как Mac. Нужна граница точного семейства ОС; неподтверждённые ОС не должны превращаться в уверенную модель.
5. **Потеря легитимной модели при фильтрации (воспроизводимо по `_safe`):** названия со слешем, например `Samsung SM-S928B/DS`, и строки свыше 48 символов заменяются на платформенный fallback; исходную модель нельзя без проверки пропускать в клиентский интерфейс. Конкретное правило разрешённых hardware model tokens следует отдельно оценить с regression/security tests.
6. **Android каталог: риск ложного сопоставления, не подтверждённый production:** индекс `_android()` использует только столбец `Device` и проверяет уникальность `Marketing Name`, но не проверяет `Retail Branding`/столбец `Model` для текущей записи. Контекст производителя/модели может потребоваться при коллизиях; нельзя приписывать случайную коммерческую модель по первому совпадению. В рамках этого read-only аудита полный 54k-строчный каталог отдельно не проанализирован.
7. **Apple/macOS:** точный `iPhone18,1` может сопоставляться по Apple catalog при подтверждённом iOS, а `iphone18,1` (другой регистр) не проходит case-sensitive `_APPLE_ID`; неопознанный код может остаться в карточке. При macOS коммерческая iPad-модель сохраняется, если не является точным `iPad` или Model ID (наблюдение F5).
8. **Unknown OS:** отсутствие `deviceOs` при составном UA OneXray не является основанием объявить iOS по хвосту `ios`; `ОС неизвестна` — правильный fail-safe без независимого источника ОС.
