## Статусы дорожной карты

Дорожная карта ведётся как постоянно обновляемый документ. Для пунктов, по которым уже началась реализация, используется явный статус:

- `⬜ Запланировано` — работа ещё не завершена в `main`;
- `🟡 Реализовано в main` — код/документация уже слиты, но соответствующий release ещё не опубликован;
- `🟠 Опубликовано; acceptance отложен` — релиз опубликован, но обязательный production acceptance, targeted smoke или recovery drill остаётся незавершённым; факт deployment указывается отдельно, без привязки к v4.x/v5.x;
- `✅ Выполнено в vX.Y.Z` — изменение опубликовано в указанном релизе и обязательный acceptance scope закрыт.

Статус меняется только по фактическому состоянию репозитория. Merge в `main` не считается опубликованным релизом, а публикация release без завершённого acceptance scope не должна автоматически закрывать пункт.

### Учёт слитых изменений и остатка проверок

Актуальная верхняя сводка — единый реестр значимых доработок, багфиксов, security/operational changes и оставшихся обязательств по приёмке. После merge, публикации, deployment и каждой значимой проверки сверяй её с фактами. До фактического merge не называй PR слитым; если обновление статуса требует отдельного docs-only PR, зафиксируй его до следующей работы по пункту или подготовки release. Подробный workflow: [GIT_WORKFLOW.md](GIT_WORKFLOW.md#ведение-roadmap).

Для каждого затронутого пункта должны быть доступны **Issue/PR и краткий результат**, **состояние в `main` / GitHub Release / production**, **уже проверенный scope с evidence**, **оставшийся scope или блокер**, **следующее действие**. Существующие таблицы и датированные разделы могут использовать разные представления этих полей; дублировать одни и те же данные в новой таблице не требуется. При очередной сверке указывай дату, версию/tag/SHA там, где это важно.

`PASS`, `PARTIAL`, `PENDING`, `FAIL`, `BLOCKED` относятся **к отдельным проверкам**, а не заменяют четыре статуса Roadmap. Частичная проверка, зелёный CI, manual smoke, публикация RC или отсутствие новых жалоб не являются доказательством полного production acceptance. Нельзя закрывать обязательный gate без подтверждённого результата; manual и scheduled проверки, DR preflight и isolated restore учитываются отдельно.

Новые факты дополняют актуальную сводку и исторические evidence, не переписывая более ранние наблюдения. Для детальных production canary/acceptance результатов используются соответствующие `docs/audits/**` и профильные runbooks; secrets и приватные идентификаторы туда не переносятся.
